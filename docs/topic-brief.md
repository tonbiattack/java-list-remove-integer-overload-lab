# 題材企画: `List<Integer>.remove`が値ではなくインデックスを削除する

## 対象

| 項目 | 内容 |
| --- | --- |
| 対象言語 | Java 21 |
| 対象読者 | `List<Integer>`から識別子を削除するとき、`remove(int)`と`remove(Object)`のオーバーロードを見落としやすい中級者 |
| 難易度プロファイル | 実践・上級 |
| 選定理由 | `List`には位置を削除する`remove(int)`と、最初に一致する要素を削除する`remove(Object)`がある。`int`変数を渡すと前者が選ばれるため、待機ジョブIDを削除するつもりで別のジョブを削除できる。戻り値、残った待機ID、削除履歴を分けて観測し、型・オーバーロード・インデックスの仮説を比較できる。 |
| 実行基盤 | Maven、Java 21、JUnit Jupiter 5.11.4 |
| フレームワーク非依存性 | 原因は`java.util.List`の標準ライブラリ契約とJavaのオーバーロード解決である。HTTP、DI、DB、外部APIには依存しない。 |

## 学習する契約

> 待機ジョブIDが`[1, 2, 3]`で、ID`1`の取消を依頼した場合、ID`1`を取り除いて`[2, 3]`にし、削除履歴を`[1]`へ更新すべきだが、バグ状態ではインデックス1のID`2`が取り除かれ、待機ID`[1, 3]`と削除履歴`[2]`が残る。

### 対象の直接原因

`int jobId`をそのまま`pendingJobIds.remove(jobId)`へ渡している。`List`の`remove(int)`が選択され、`jobId`を要素値でなくゼロ始まりの位置として扱う。

### 対象外

このラボはジョブ実行、並行処理、キュー実装、永続化、重複ID、負値や範囲外値の例外変換、キャンセル権限を扱わない。インメモリの`ArrayList<Integer>`から、既知の整数IDを削除する狭い規則だけを扱う。

## 再現設計

| 要素 | 決定 |
| --- | --- |
| 公開境界 | `PendingJobRegistry#cancel(int)`、`pendingJobIds()`、`cancellationHistory()`。 |
| 入力・初期状態 | 待機IDを`[1, 2, 3]`とし、ID`1`を取消する。 |
| Redの観測 | `CancellationOutcome.CANCELLED`を期待するが、バグ状態では同じ結果コードのまま、状態が`[1, 3]`と`[2]`になる。 |
| 最終観測 | `pendingJobIds()`が`[2, 3]`となり、`cancellationHistory()`が`[1]`であることを別々に検証する。 |
| 決定性 | 時刻、乱数、並行実行、`sleep`、外部I/Oを使わず、固定の整数値とインメモリListだけを使う。 |
| 固定状態の検証コマンド | `mvn --batch-mode clean test` |
| バグ状態の確認コマンド | `git checkout <bug-commit>`後に`mvn --batch-mode test -Dtest=PendingJobRegistryTest` |

## 仮説

| 仮説 | どう検証または除外するか |
| --- | --- |
| A: ジョブIDが待機Listに存在しない | 取消前に`[1, 2, 3]`であることを確認する。 |
| B: 取消履歴への追記が壊れている | 戻り値として受け取った削除値とListの残存値を直接観測する。 |
| C: `int`引数により`remove(int)`が選ばれる | 同じListで`remove(1)`と`remove(Integer.valueOf(1))`を比較する。 |

## 予定する履歴

| 順序 | コミットの目的 | 期待する状態 |
| --- | --- | --- |
| 1 | ジョブIDの取消で別のIDを削除する失敗を再現する | 対象テストが待機ID`[2, 3]`期待・`[1, 3]`実際のアサーション差分で失敗する。 |
| 2 | ジョブIDを要素値として削除する | 同じ検証が成功し、全体も成功する。 |
